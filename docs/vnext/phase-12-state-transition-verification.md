# Phase 12 — State Transition Verification

Status: **staged vNext PPMC hardening; not canonical HTTP/product runtime wiring**.

## Scope

Phase 12 audited whether PPMC validates the same disclosure state and state-bound governance
semantics that its transition engine and forbidden-state evaluator actually consume.

The audit concentrated on:

- `DisclosureState` canonical revalidation versus runtime transition reads;
- snapshot transitions and the declared snapshot graph;
- purpose, governance, and evidence commitments carried by state;
- state reconstruction and `state_sha256` commitments;
- F6 governance binding semantics;
- semantic/composition transitions generated by the security-owned Future Action Grammar;
- BFS visited-state identity versus the security semantics evaluated at each node;
- polymorphic Pydantic models, virtual `model_dump()`, and unsafe `model_construct()` paths.

Phase 12 found two real false-negative gaps and closed both at the public PPMC trust boundary.

## Proven gap 1 — polymorphic DisclosureState transition split

The internal PPMC engine canonical-revalidated the supplied initial state with:

`DisclosureState.model_validate(initial_state.model_dump(mode="json"))`

but then placed the original caller-supplied object into the BFS queue. Transition application and
path construction subsequently read fields directly from that original object, including the
warehouse snapshot and state-bound commitments.

The initial red TDD head was:

`f51a8a62db2169b82e6afa1aaa56ec3482fcd639`

The regression reused the existing Day-8 hard-gate fixture. The legitimate state deterministically
produces the known depth-2 F5 counterexample:

`SNAPSHOT_ADVANCE -> REPLAY`

A malicious `DisclosureState` subclass then:

1. returned the legitimate state's bytes from virtual `model_dump()`;
2. retained the legitimate `state_sha256` already committed by the grammar;
3. exposed a different runtime-only `warehouse_snapshot_sha256` outside the declared snapshot graph.

Canonical revalidation therefore validated the legitimate serialized state, while
`apply_future_action()` consumed the divergent runtime state. Every declared transition was rejected
against that runtime-only snapshot, the local oracle was never reached, and PPMC returned
`NO_COUNTEREXAMPLE_WITHIN_BOUND` instead of the real `PROSPECTIVE_UNSAFE` counterexample.

The red CI result on both Python 3.11 and Python 3.12 was:

`1 failed, 816 passed`

with the explicit failure:

`PPMC accepted a polymorphic DisclosureState and certified safety after runtime-only state semantics pruned the declared transition graph`

This is a real validated-state / searched-state type-confusion false negative, not a state-hash-only
mismatch.

## Fix 1 — exact DisclosureState at the public PPMC boundary

`toxicjoin.prospective.ppmc.check_prospective_privacy()` now requires the exact
`DisclosureState` type before internal canonical serialization or BFS transition processing.

The existing Pydantic canonical revalidation still runs after the exact-type gate. This is
intentional: the exact-type check blocks virtual serialization substitution, while canonical
revalidation still rejects exact `DisclosureState` instances corrupted through unsafe construction
paths such as `model_construct()`.

No alternate state builder or second transition engine was introduced.

## Proven gap 2 — polymorphic GovernanceTrustBinding F6 split

The same audit found a second split in the state-bound governance input.

The internal PPMC revalidation serialized `GovernanceTrustBinding`, but F6 later evaluated the
original object directly. The second red TDD head was:

`10e6150147e8b2b7fb51ab7f394e5b5bed554e2c`

The regression first proved that an exact binding with `trusted=False` produces an immediate F6
`PROSPECTIVE_UNSAFE` result. A malicious subclass then:

1. serialized exactly as that untrusted binding;
2. retained its legitimate `binding_sha256`;
3. exposed runtime `trusted=True` to F6.

PPMC accepted the object, F6 consumed the divergent runtime trust value, and the bound-zero check
returned `NO_COUNTEREXAMPLE_WITHIN_BOUND`.

The red Python 3.11 result was:

`1 failed, 818 passed`

with the explicit failure:

`PPMC accepted a polymorphic GovernanceTrustBinding and cleared F6 using runtime trust semantics that differed from canonical revalidation`

Python 3.12 failed the same regression.

## Fix 2 — exact state-bound governance input

The public PPMC boundary now rejects a polymorphic `GovernanceTrustBinding` before internal
canonical serialization. `None` remains valid so the existing F6 missing-binding semantics are
unchanged.

As with `DisclosureState`, internal canonical Pydantic revalidation remains active and rejects an
exact `GovernanceTrustBinding` corrupted through `model_construct()` while retaining a stale hash.

## State-transition audit results

### Snapshot transitions

`apply_future_action()` requires the current state to remain inside the grammar model universe and
requires a snapshot action's declared source to match the current warehouse snapshot. Snapshot edges
are instantiated from the canonical grammar context. After the new state exact-type gate, the
snapshot value validated at the public boundary is the value consumed by transition processing.

### Purpose, governance, and evidence commitments

The transition model-universe check requires the state's purpose commitment, governance commitment,
and evidence root to equal the committed grammar context. `state_sha256` also commits these fields.
The exact-state gate prevents a root polymorphic object from presenting one serialized commitment
set while exposing another set to transition processing.

### Semantic and composition transitions

Release transitions are selected from the exact, canonical Future Action Grammar hardened in Phase
11. Transition processing requires the supplied action to match a canonical grammar member, projects
its semantic/composition pair into direct disclosure atoms, merges those atoms canonically, and then
rebuilds the state.

No additional semantic/composition transition gap was proven in Phase 12.

### State reconstruction

`_rebuild_state()` recomputes inference rules, deterministic least-fixed-point derived atoms, the
inference-rule commitment, and the resulting `state_sha256`, then constructs a validated exact
`DisclosureState`.

Therefore BFS-produced child states do not inherit a caller-supplied state hash without recomputing
security semantics.

### Nested state models

Adversarial probes placed polymorphic `DisclosureScope` and `DisclosureAtom` instances inside an
exact root `DisclosureState`, with runtime values differing from the legitimate objects they tried to
represent.

The existing canonical state revalidation rejected those objects. No nested virtual-serialization
bypass was demonstrated, so Phase 12 did not add broader nested exact-type gates without evidence.

### BFS visited-state identity

The BFS node key is:

`(state.state_sha256, temporal_signature_sha256)`

The state hash commits scope, purpose, governance, evidence root, warehouse snapshot, released atoms,
derived atoms, and inference-rule commitment.

The temporal signature commits the set of sensitive `(release_semantic_sha256,
warehouse_snapshot_sha256)` pairs. F5 temporal differencing is itself determined by whether one
sensitive release semantic appears across at least two distinct warehouse snapshots; it does not use
path ordering to decide MATCHED versus CLEAR.

Because forbidden-state evaluation is state-based for F1-F4/F6 and set-based for F5, the audited
visited-state identity does not collapse two nodes with different safety outcomes under the current
predicate semantics. No visited-state false-negative was proven.

## Adversarial regression set

Phase 12 now covers:

- root polymorphic `DisclosureState` with legitimate virtual serialization and divergent runtime
  snapshot semantics;
- exact `DisclosureState` corrupted through `model_construct()`;
- nested polymorphic `DisclosureScope` inside an exact state;
- nested polymorphic `DisclosureAtom` inside an exact state;
- polymorphic `GovernanceTrustBinding` whose serialized trust value differs from runtime F6 trust;
- exact `GovernanceTrustBinding` corrupted through `model_construct()`.

The existing Day-8 hard-gate fixture remains the positive reference: the legitimate state still
produces the depth-2 `SNAPSHOT_ADVANCE -> REPLAY` F5 counterexample.

## Claim boundary

Phase 12 does **not**:

- change the configured PPMC bound or state budget;
- claim unbounded prospective safety;
- change the forbidden-predicate policy thresholds;
- change the Future Action Grammar action universe established in Phase 11;
- change PolicyEngine semantics;
- change DataHub behavior or Agent privileges;
- change disclosure-ledger persistence;
- make `ProofBoundExecutionAuthorizer` canonical;
- wire staged PPMC or the Governed Agent into the current HTTP/product execution path;
- change the canonical legacy `ExecutionAuthorizer`.

`docs/security-architecture.md` remains the canonical current-runtime truth. Phase 12 remains staged
vNext security hardening until a later explicit migration phase changes product wiring.

Resource-safety properties of PPMC search configuration remain Phase 13 scope and are not expanded by
this phase.
